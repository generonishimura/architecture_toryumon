# 第5回 ドメイン駆動設計（DDD）：講師補助資料

## この回のキーメッセージ

> 「ビジネスの言葉でコードを書くことが、最も強力な設計手法」

知識レベルA（実務経験必須）の回。DDDは概念が広く抽象度も高いため、「戦略的設計の概要 → 戦術的設計の具体コード」の順に進め、抽象的な説明だけで終わらないよう、具体例やコードと結びつけて説明する。

## 各トピックの教え方のポイント

### ユビキタス言語
- 「開発者が『user_order_record』と呼んでいるものを、ビジネスサイドは『注文』と呼ぶ。このズレがあると、ビジネスの理解とコードの設計が食い違っていく」
- コード上の名前にもユビキタス言語をそのまま使う、という原則を強調する
- **実演:** 参加者に「自分のプロジェクトで、開発者とビジネスサイドで呼び方が違うものは？」と聞く

### 境界づけられたコンテキスト
- READMEのコンテキストマップ図を使いながら説明
- 「同じ『商品』でもカタログと在庫で意味が違う」が最も伝わりやすい例
- ACL（腐敗防止層）は第4回のAdapterパターンの応用であることを示す
- **注意:** コンテキスト間の関係パターン（共有カーネル、顧客/供給者等）は深入りしすぎない。名前と概要だけでOK

### エンティティ vs 値オブジェクト
- 要点は **「同一性で比較する」vs「値で比較する」** の違い
- 例:「田中太郎さんが名前を田中花子に変えても同一人物（エンティティ）」「1000円は別の1000円と区別しない（値オブジェクト）」
- TypeScriptコードで `equals()` の実装を見せると具体的になる

### 集約
- **この回で最も理解が難しく、最も議論になるポイント**
- 「集約は小さく保つ」原則を繰り返し強調する
- Order集約の例: Order（集約ルート）→ OrderItem（内部エンティティ）→ Money（値オブジェクト）
- **問いかけ:** 「Order集約にCustomer情報を含めるべきか？含めると何が問題か？」

### ドメインイベント
- 「OrderPlaced」「PaymentCompleted」のように過去形で命名
- 第9回（イベント駆動）で再び使う内容。「ここで学んだドメインイベントがサービス間通信の基盤になる」と予告する

## コード課題のレビュー観点

- 「同じ客室の同一日程に複数の予約はできない」を、参加者が(a)と(b)のどちらで守ったかを確認する
- (a)客室ごとの予約台帳を集約にする：ルールが1つの集約の中で完結する。ただし集約が大きくなり、同じ客室への同時予約が競合エラーになりやすい
- (b)ドメインサービスとDBの一意制約・排他制約を組み合わせる：Reservation集約は小さいままにできる。ただしルールの一部がDBの制約に置かれるので、ドメインモデルだけを読んでもルールの全体が分からない
- どちらを選んだ場合も、選んだ理由が書かれていれば正解とする
- キャンセル期限の判定で、現在日時を引数で受け取っているか（メソッドの中で `new Date()` を呼んでいないか）を確認する

## 想定される質問と回答例

| 質問 | 回答の方向性 |
|------|-------------|
| 「DDDは全プロジェクトに適用すべき？」 | 「ビジネスロジックが複雑な場合に効果が大きい。CRUDが中心の管理画面では手間に見合わない。ドメインの複雑さに応じて適用度を変える」 |
| 「集約をどのくらいの大きさにすべきか分からない」 | 「1つのトランザクションで整合性を保つ必要がある範囲。迷ったら小さく作って、後から必要に応じて広げるほうが安全」 |
| 「値オブジェクトのimmutableはコスト高くない？」 | 「JavaScriptのプリミティブ（string, number）も不変。同じ感覚で。パフォーマンス問題は実際に計測してから考える」 |
| 「DBのテーブルとドメインモデルは1対1？」 | 「必ずしも一致しない。集約を1テーブルにマッピングするとは限らない。第6回のクリーンアーキテクチャでこの分離をさらに詳しく扱う」 |

## 多角的な視点

### ビジネスサイドとの協働
- DDDで最も価値が大きいのは、ビジネスサイドと技術サイドが「同じ言葉」で会話できるようになること。技術的な実装パターンはその次
- ユビキタス言語をコード上の名前に使うと、コードを読めないビジネスサイドの人にも、クラス名やメソッド名から設計の意図が伝わる
- 実際のプロジェクトでDDDがうまくいくかどうかは、ドメインエキスパートと定期的に話す場を持てるかどうかで決まることが多い

### 既存プロジェクトへの段階的導入
- 「全面的にDDDで書き直す」のは現実的でない場合が多い。次の順で段階的に導入する方法を紹介する
  1. まずユビキタス言語の整理から始める（コードを変更せずに始められる）
  2. 新規機能から値オブジェクトを導入する
  3. ビジネスロジックが複雑な箇所にエンティティ・集約を適用する
  4. 必要に応じて境界づけられたコンテキストを明確にする
- 「DDDのすべてを一度に導入する必要はない」と伝えると、参加者が感じるプレッシャーを減らせる

### データモデルとドメインモデルの関係
- 第3回で学んだデータモデルと、DDDのドメインモデルは別のものであることをはっきり伝える
- テーブル構造とドメインオブジェクトが1対1対応しないケース（集約を複数テーブルにマッピングする等）を具体例で示す
- 「データ中心設計」と「ドメイン中心設計」の違いを対比する
