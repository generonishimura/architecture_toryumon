## 各トピックの教え方のポイント

### 正規化
- **最初に非正規化されたテーブルを見せる。** 「何が問題か？」を参加者に考えさせてから正規形を説明する
- 更新時異常を具体的に示す。たとえば「このテーブルでユーザーの住所を変更するとき、何行更新が必要？」と問いかける
- 第3正規形まででOK。BCNFや第4正規形は深追いしない

### インデックス
- B-Treeの図を簡略的に描き、列の値が順番に並んでいるので、テーブルを先頭から全部読まなくても目的の行を探せることを示す
- **複合インデックスのカラム順序が最重要ポイント。** `(user_id, status)` と `(status, user_id)` で効くクエリが違うことを実例で示す
- 「インデックスを張れば速くなる」という思い込みを訂正する。インデックスには書き込みコストとストレージコストがかかる

### トランザクション分離レベル
- ダーティリード → ノンリピータブルリード → ファントムリードの順に、具体的な業務シナリオで示す
- 「銀行の送金処理」が最も分かりやすい例
- 分離レベルのデフォルト値がPostgreSQL（READ COMMITTED）とMySQL（REPEATABLE READ）で異なることは実務で重要

### デッドロック
- 「2つのトランザクションが互いのロックを待つ」を図で示す
- 防止策: ロック順序の統一、トランザクションを短くする。検出時の対処: DBがデッドロックを検出して片方をエラーにするので、アプリは回数に上限を付けてトランザクションを最初から再試行する（ロック待ちのタイムアウトは、待ち続けることを防ぐ対策で、デッドロックの防止策ではない）

## 実演・デモのアイデア

- **EXPLAIN ANALYZEのライブデモ:** 同じクエリにインデックスあり/なしで実行し、実行時間の差を見せる
- **デッドロック再現デモ:** 2つのターミナルで交差するUPDATEを実行し、デッドロックを実際に発生させる。READMEの送金処理（`transfer`）をそのままA→BとB→Aで同時に実行しても、デッドロックはほとんど起きない。`transfer` の中では2つのUPDATEが間を置かずに続けて実行されるためである。確実に再現するには、1つ目のUPDATEのあとに待ち時間（例: `await new Promise(r => setTimeout(r, 1000))` や `SELECT pg_sleep(1)`）を入れてから、A→BとB→Aの送金を同時に実行する。口座IDの小さい順に更新すれば起きないことも示す
- **非正規化テーブルの更新異常デモ:** 「住所を変更するのに5行更新が必要」を実際に見せる

## 多角的な視点

### 運用・パフォーマンスの観点
- 本番環境のDBは、設計したあとも運用しながら見直す。スロークエリの監視、定期的なEXPLAINの確認、使われていないインデックスの確認などを通じて、設計を改善する
- 「インデックスは貼ればいいわけではない」と伝える。不要なインデックスはINSERT/UPDATEを遅くし、ストレージの容量も使う。これを実例で示す
- パーティショニング、レプリケーション（読み取りレプリカ）の概要にも軽く触れると、フェーズ3（分散システム編）の予告になる

### ORM利用時の注意点
- ORMを使うと「SQLを書かなくてよい」と思われがちだが、N+1問題や不必要なSELECT *が起きることがある。ORMが生成するSQLを確認する必要があると伝える
- Prisma はリレーションを自動では遅延読み込み（lazy loading）しない。`include` を付けると関連を一緒に取得し、付けないと取得しない。N+1は、`findMany` の結果をループして、行ごとに関連を `findMany` すると起きる。`new PrismaClient({ adapter, log: ['query'] })` で発行されるSQLを表示し、`include` を使う場合とループで取得する場合のクエリ数の違いを見せる
- 「ORMに任せきりにせず、重要なクエリはEXPLAINで確認する」習慣を推奨する

### データの長期的な価値
- 「アプリケーションコードは書き直せるが、データは書き直せない」という点から、データモデルが事業にとって重要であることを伝える
- データモデルが正しければ、UIやアプリを作り直しても、データはそのまま使い続けられる
