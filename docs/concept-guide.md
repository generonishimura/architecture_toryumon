## 1. 全体の地図

本ワークショップで扱う概念は、下の図の上から順に、扱う範囲（スケール）が段階的に大きくなります。

```
スケール    扱う範囲                対応する概念
─────────────────────────────────────────────────────────
  小        1つのクラス・関数       オブジェクト指向、SOLID原則
  ↓         1つのテーブル・DB       RDB、データモデリング
  ↓         複数クラスの連携        デザインパターン
  ↓         1つのドメイン           ドメイン駆動設計 (DDD)
  ↓         1つのアプリケーション    クリーンアーキテクチャ
  ↓         複数のサービス          マイクロサービス
  ↓         インフラ・デプロイ      オーケストレーション
  大        サービス間通信          イベント駆動アーキテクチャ
```

各概念は、それぞれ独立してはいません。前の概念を理解していることが、次の概念を理解する前提になるように並べてあります。

### なぜこの順番なのか

- SOLID原則を知らなければ、デザインパターンの価値がわからない
- デザインパターンを知らなければ、DDDの実装が想像できない
- DDDの境界づけられたコンテキストを知らなければ、マイクロサービスの分割判断ができない
- クリーンアーキテクチャを知らなければ、各サービスの内部構造が設計できない

前の回で学んだ内容を次の回で使う構成が、本ワークショップの最大の特徴です。

## 2. オブジェクト指向設計

### この概念が解決する問題

> 「コードを修正したら、関係ないはずの場所が壊れた」

これは、ソフトウェア開発で特によくある悩みです。原因の多くは、責務の境界が曖昧で、依存関係が制御されていないことです。

### 中心となる2つの仕組み：カプセル化とポリモーフィズム

オブジェクト指向設計で中心になるのは「継承」ではありません。カプセル化とポリモーフィズムの2つです。

**カプセル化**：内部の状態を隠し、外部にはインターフェース（操作方法）だけを公開します。

```
┌──────────────────────┐
│  BankAccount          │
│  ─────────────────    │
│  - balance: number    │  ← 外からは直接触れない
│  ─────────────────    │
│  + deposit(amount)    │  ← 公開された操作を通じてのみ変更
│  + withdraw(amount)   │
│  + getBalance()       │
└──────────────────────┘
```

カプセル化しておくと、内部の実装（balanceをどう管理するか）を変更しても、外部のコードを修正せずに済みます。

**ポリモーフィズム**：同じインターフェースで、異なる振る舞いを実現します。

```
         ┌───────────────┐
         │  <<interface>> │
         │  Notifier      │
         │  + send()      │
         └───────┬───────┘
           ┌─────┼─────┐
           ▼     ▼     ▼
        Email  Slack   SMS
        Notif  Notif   Notif
```

呼び出す側のコードは、send()を呼ぶだけです。メール・Slack・SMSのどれで送るかは、実行時に決まります。

### SOLID原則：良い設計の5つの指針

| 原則 | 一言で言うと | 身近な例え |
|------|------------|-----------|
| **S**：単一責任 | 1つのクラスに1つの理由で変更 | 「料理人は料理だけ、会計は会計だけ」 |
| **O**：開放閉鎖 | 既存コードを修正せず拡張できる | 「コンセントに新しい家電を挿すだけ」 |
| **L**：リスコフの置換 | 親クラスの代わりに子クラスを使える | 「アルバイトでも正社員でも同じマニュアルで動ける」 |
| **I**：インターフェース分離 | 使わないメソッドに依存させない | 「リモコンのボタンは必要なものだけ」 |
| **D**：依存性逆転 | 具体ではなく抽象に依存する | 「家電メーカーではなく、家の側がコンセント規格を決める」 |

5つの原則の中で最も重要な原則は、**依存性逆転の原則（DIP）** です。このあと扱う概念はすべて、DIPを理解していることを前提にしています。

### 依存性逆転の原則（DIP）をさらに詳しく

DIPを適用しない通常の依存は、次の向きです。

```
OrderService ──依存──▶ MySQLDatabase
```

この場合、データベースを変更すると、OrderServiceも修正する必要があります。

DIPを適用すると、依存は次のようになります。

```
OrderService ──依存──▶ <<interface>> OrderRepository ◀──実装── MySQLOrderRepository
```

OrderServiceは「データの保存・取得」という抽象だけに依存します。そのため、OrderServiceのコードには、MySQLとPostgreSQLのどちらを使うかが書かれていません。この形にすることを、**依存の方向を逆転**させると言います。

DIPでは、OrderRepositoryインターフェースを「使う側」が定義し、所有します。使う側とは、上位モジュールであるOrderServiceの側です。MySQLOrderRepositoryは、そのインターフェースをimplementsします。そのため、ソースコードの依存は MySQLOrderRepository → OrderRepository（上位側）の向きになります。適用前の依存は、上位 → 下位の向きでした。この向きが反対になることを「逆転」と呼びます。インターフェースを挟んでも、下位側がそのインターフェースを定義しているなら、依存は逆転していません。

### 後続の概念とのつながり

- デザインパターン → GoFパターンはOOPの設計テクニックそのもの
- DDD → エンティティ、値オブジェクトはOOPのクラス設計が前提
- クリーンアーキテクチャ → DIPでレイヤー間の依存の向きを制御する

## 3. リレーショナルデータベース

### この概念が解決する問題

> 「アプリは動いているが、データが壊れていた」

ソフトウェアで最も価値があるのは**データ**です。コードはいつでも書き直せますが、壊れたデータは復元できません。RDBは、制約やトランザクションの仕組みで、データの整合性を保つ技術です。

### 正規化でデータの重複を取り除く

正規化とは、データの冗長性を排除し、更新時の矛盾を防ぐ手法です。

```
【正規化前】注文テーブル
┌────────┬──────────┬────────────┬──────────┐
│ 注文ID  │ 商品名    │ 顧客名      │ 顧客住所  │
├────────┼──────────┼────────────┼──────────┤
│ 001    │ ノートPC  │ 田中太郎    │ 東京都... │
│ 002    │ マウス    │ 田中太郎    │ 東京都... │  ← 顧客情報が重複！
└────────┴──────────┴────────────┴──────────┘

田中さんが引っ越したら、すべての行を更新する必要がある
→ 1行でも更新漏れがあるとデータ不整合

【正規化後】
注文テーブル                 顧客テーブル
┌────────┬──────┬───────┐   ┌───────┬──────────┬──────────┐
│ 注文ID  │ 商品ID│ 顧客ID │   │ 顧客ID │ 顧客名    │ 顧客住所  │
├────────┼──────┼───────┤   ├───────┼──────────┼──────────┤
│ 001    │ P01  │ C01   │   │ C01   │ 田中太郎  │ 東京都... │
│ 002    │ P02  │ C01   │   └───────┴──────────┴──────────┘
└────────┴──────┴───────┘
```

| レベル | 要件 | 平たく言うと |
|--------|------|------------|
| 第1正規形 | 繰り返し項目の排除、値の原子性 | 「1つのセルに1つの値」 |
| 第2正規形 | 部分関数従属の排除 | 「主キーの一部だけに依存する列を分離」 |
| 第3正規形 | 推移的関数従属の排除 | 「主キー以外の列に依存する列を分離」 |

### インデックス：検索を高速化する仕組み

インデックスは、列の値から行の位置を探すための索引です。インデックスを使うと、テーブルの全行を読まなくても目的の行を見つけられます。

```
インデックスなし: テーブル全行を順番にスキャン → O(n)
インデックスあり: B-Treeで効率的に検索      → O(log n)

100万行のテーブル:
  全行スキャン → 100万回の比較
  B-Tree検索   → 約20回の比較
```

インデックスには注意点があります。インデックスを作ると読み取りは速くなりますが、書き込みのたびにインデックスも更新するため、書き込みのコストが増えます。そのため、インデックスは**よく検索される列**にだけ作ります。

### トランザクションとACID特性

トランザクションは **「一連の操作を全部成功させるか、全部なかったことにするか」** を保証する仕組みです。

```
銀行の送金処理:
  1. Aさんの口座から1万円引く
  2. Bさんの口座に1万円足す

→ 1だけ成功して2が失敗したら、1万円が消える！
→ トランザクションなら、2が失敗した時点で1も取り消される
```

| 特性 | 意味 | 例え |
|------|------|------|
| **A**：原子性 | 全部成功 or 全部失敗 | 「途中で止まらない」 |
| **C**：整合性 | 制約が常に満たされる | 「残高はマイナスにならない」 |
| **I**：分離性 | 他のトランザクションの影響を制御 | 「他の人の処理中を見えなくする」 |
| **D**：永続性 | コミットしたデータは消えない | 「確定した取引は記録される」 |

### 後続の概念とのつながり

- データモデリング → 正規化の知識が概念モデルから物理モデルへの変換に必須
- DDD → リポジトリパターンで、ドメインモデルとDBの間の変換を受け持つ
- マイクロサービス → Database per Serviceパターンの設計判断に、RDBの知識を使う

## 4. データモデリング

### この概念が解決する問題

> 「テーブル設計から始めたが、ビジネスの要件変更のたびに大改修が必要になる」

テーブル設計（物理モデル）からいきなり始めると、ビジネスの構造よりも、技術の制約に合わせた設計になります。データモデリングでは、先にビジネスを正確に構造化し、そのあとで特定の技術に合わせた設計に変換します。

### 3段階のモデリング

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  概念モデル    │ ──▶ │  論理モデル    │ ──▶ │  物理モデル    │
│              │     │              │     │              │
│ ビジネスの    │     │ データ構造の  │     │ DB固有の      │
│ エンティティと │     │ 正規化・型    │     │ 型・制約・     │
│ 関係を整理    │     │ の決定       │     │ インデックス    │
│              │     │              │     │              │
│ 技術を       │     │ 特定のDBに   │     │ 実際のDB    │
│ 考えない      │     │ 依存しない    │     │ に合わせる    │
└──────────────┘     └──────────────┘     └──────────────┘
  WHO / WHAT            HOW (論理)          HOW (実装)
```

3段階に分ける理由は、段階ごとに考えることが違うからです。

- 概念モデルで、何が重要かを明確にする（ビジネスとの認識合わせ）
- 論理モデルで、データの関係を厳密にする（正規化の適用）
- 物理モデルで、パフォーマンスを考慮する（インデックス、非正規化の判断）

いきなり物理モデルを書くと、「このテーブルは何のために存在するのか」が曖昧になります。その結果、あとからテーブルを変更するのが難しくなります。

### ER図の読み方

```
  ┌──────────┐    1    N    ┌──────────┐
  │  Author   │────────────│  Book     │
  │  著者     │            │  書籍     │
  └──────────┘             └──────────┘

  「1人の著者は N冊の本を書く。1冊の本は1人の著者が書く」

  多対多の場合 → 中間テーブルで分解

  ┌──────────┐    N    N    ┌──────────┐
  │  Student  │────────────│  Course   │
  │  学生     │            │  講座     │
  └──────────┘             └──────────┘
                  ↓ 分解
  Student  ──1:N──  Enrollment  ──N:1──  Course
                    （受講登録）
```

### 後続の概念とのつながり

- DDD → ドメインモデルは概念モデルをもとに作る。エンティティと値オブジェクトを区別する考え方は、概念モデリングで身につく
- マイクロサービス → サービスごとのデータの分け方は、概念モデルで決めたエンティティの境界をもとに決める

## 5. デザインパターン

### この概念が解決する問題

> 「設計レビューで指摘されるが、どう直せばいいかわからない」

デザインパターンは、ソフトウェア設計で繰り返し現れる問題について、再利用できる解決策に名前をつけたものです。パターンを知っていると、設計の問題に気づきやすくなり、解決策を名前で説明できるようになります。

### GoFパターンの3つのカテゴリ（と、GoF以外の重要パターン）

GoF（Gang of Four）は23のパターンを、生成・構造・振る舞いの3つに分類しました。

```
┌────────────────────────────────────────────────────────────────────┐
│                  GoF のデザインパターン（23種類）                  │
│                                                                    │
│  ┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐  │
│  │ 生成パターン     │  │ 構造パターン     │  │ 振る舞いパターン │  │
│  │                  │  │                  │  │                  │  │
│  │ オブジェクト     │  │ オブジェクト     │  │ オブジェクト間の │  │
│  │ の作り方         │  │ の組み合せ方     │  │ 責務の分担       │  │
│  │                  │  │                  │  │                  │  │
│  │ • Factory        │  │ • Adapter        │  │ • Strategy       │  │
│  │   Method         │  │ • Facade         │  │ • Observer       │  │
│  │ • Abstract       │  │                  │  │                  │  │
│  │   Factory        │  │                  │  │                  │  │
│  │ • Builder        │  │                  │  │                  │  │
│  └──────────────────┘  └──────────────────┘  └──────────────────┘  │
└────────────────────────────────────────────────────────────────────┘

┌─ GoF以外の実務パターン ────────────────────────────────────────────┐
│                                                                    │
│  • Repository（Fowler『PoEAA』2002 / Evans『DDD』2003）            │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

Repositoryは、GoFのパターンではありません。Martin Fowlerの『エンタープライズアプリケーションアーキテクチャパターン（PoEAA）』（2002）で定義されたパターンです。Eric Evansの『ドメイン駆動設計（DDD）』（2003）でも定義されています。本ワークショップでは、第4回で「GoF以外の実務パターン」として扱います。

### 重要パターンの直感的理解

**Strategy（戦略）パターン**：アルゴリズムを差し替えられるようにする

```
問題: if文の分岐が増え続ける
  if (type === "regular") { ... }
  else if (type === "member") { ... }
  else if (type === "vip") { ... }    ← 新しい種別を追加するたびに修正

解決: 戦略を別クラスに分離
  PriceCalculator → PricingStrategy(interface)
                        ├── RegularPricing
                        ├── MemberPricing
                        └── VIPPricing    ← 追加しても既存コードは変更不要
```

**Repository（リポジトリ）パターン**：データアクセスを抽象化する

```
問題: ビジネスロジックの中にSQL文が埋め込まれている
  → DBを変更すると、ビジネスロジックも修正が必要

解決: データアクセスをインターフェースの裏に隠す
  UseCase → Repository(interface) ← InMemoryRepo（テスト用）
                                  ← PrismaRepo（本番用）
                                  ← MockRepo（開発用）
```

**Observer（観察者）パターン**：状態変化を通知する

```
問題: 注文確定時に「メール送信」「在庫更新」「ログ記録」を実行したい
  → OrderServiceに全部書くと、責務が肥大化する

解決: 「注文確定」というイベントを発行し、各処理が個別に購読
  OrderService ──発行──▶ "OrderPlaced"
                              │
                   ┌──────────┼──────────┐
                   ▼          ▼          ▼
              EmailSender  Inventory  Logger
```

### パターン適用の心得

**「問題が先、パターンは後」**。パターンを使うこと自体を目的にしてはいけません。

```
✗ 「Factoryパターンを使おう」→ 適用先を探す
✓ 「オブジェクト生成のロジックが複雑すぎる」→ Factory が適切か検討する
```

### 後続の概念とのつながり

- DDD → Repository、Factory、Strategyをそのまま使う
- クリーンアーキテクチャ → Adapter（GoF）とGateway（PoEAA）で外部との境界を設計する
- イベント駆動 → Observerパターンの考え方を、システム全体の規模に広げる

## 6. ドメイン駆動設計

### この概念が解決する問題

> 「コードとビジネスの話が噛み合わない。開発者はテーブル名で話し、ビジネス側は業務用語で話す」

DDDは、**ビジネスの構造をそのままコードの構造にする**ための設計手法です。DDDは技術的なテクニックの集まりではありません。DDDは、ビジネスをどう理解し、どうコードに表すかについての考え方です。

### 戦略的設計と戦術的設計

```
┌──────────────────────────────────────────────────────┐
│              ドメイン駆動設計 (DDD)                     │
│                                                      │
│  ┌─────────────────────┐  ┌─────────────────────┐   │
│  │   戦略的設計          │  │   戦術的設計          │   │
│  │   (大きな構造)        │  │   (コードレベル)      │   │
│  │                     │  │                     │   │
│  │  • ユビキタス言語     │  │  • エンティティ       │   │
│  │  • 境界づけられた     │  │  • 値オブジェクト     │   │
│  │    コンテキスト       │  │  • 集約              │   │
│  │  • コンテキストマップ  │  │  • ドメインサービス    │   │
│  │                     │  │  • ドメインイベント    │   │
│  │                     │  │  • リポジトリ         │   │
│  └─────────────────────┘  └─────────────────────┘   │
│                                                      │
│     「どこで分けるか」         「中をどう作るか」        │
└──────────────────────────────────────────────────────┘
```

### ユビキタス言語：全員が同じ言葉を使う

```
✗ 開発者：「user_order テーブルの status カラムを 2 にする」
✓ 全員  ：「注文を確定する」

コードにも同じ言葉を使う:
  order.confirm()  ← 「注文を確定する」がそのままメソッド名
```

### 境界づけられたコンテキスト：同じ言葉が別の意味になる範囲

```
「商品」という同じ言葉でも、文脈によって意味が異なる:

┌─ 商品カタログ ──────┐  ┌─ 在庫管理 ──────────┐  ┌─ 配送 ────────────┐
│                    │  │                    │  │                  │
│ 商品 =             │  │ 商品 =             │  │ 商品 =           │
│  名前、説明文、     │  │  SKU、倉庫、        │  │  重量、サイズ、    │
│  画像、カテゴリ     │  │  在庫数、入荷日     │  │  配送方法         │
│                    │  │                    │  │                  │
└────────────────────┘  └────────────────────┘  └──────────────────┘

→ それぞれが独立した「境界づけられたコンテキスト」
→ 後にマイクロサービスの分割単位になる
```

### エンティティと値オブジェクト：「誰であるか」と「何であるか」

```
エンティティ（同一性で識別）         値オブジェクト（属性の組み合わせで識別）
┌───────────────────────┐        ┌───────────────────────┐
│ 注文 (Order)           │        │ 金額 (Money)           │
│ ───────────────        │        │ ───────────────        │
│ id: "ORD-001"          │        │ amount: 1000           │
│ → idが同じなら同じ注文   │        │ currency: "JPY"        │
│ → 内容が変わっても      │        │ → 1000円は1000円        │
│   同じ注文              │        │ → 区別する必要がない     │
│                        │        │ → 不変（イミュータブル） │
└───────────────────────┘        └───────────────────────┘

判断基準: 「属性が変わっても、同じものとして追跡し続ける必要があるか？」
  注文 → 明細や状態が変わっても、注文 ORD-001 として追跡する → エンティティ
  金額 → 手元の1000円札を別の1000円札と交換しても困らない → 値オブジェクト
  住所 → 顧客管理では値オブジェクトとして扱うことが多い。
         配送ルート管理のように住所そのものを追跡する文脈では、エンティティになることもある
```

### 集約：データの整合性を保つ単位

```
┌─ 注文(集約) ─────────────────────────────────────┐
│                                                  │
│  ┌──────────────────┐                            │
│  │ Order（集約ルート） │ ← 外部からのアクセスはここだけ │
│  │  id, status       │                            │
│  │  confirm()        │                            │
│  │  addItem()        │                            │
│  └──────┬───────────┘                            │
│         │ 内包                                    │
│  ┌──────┴───────────┐                            │
│  │ OrderItem         │ ← 外部から直接操作しない      │
│  │  productId        │                            │
│  │  quantity         │                            │
│  │  unitPrice        │                            │
│  └──────────────────┘                            │
│                                                  │
└──────────────────────────────────────────────────┘

ルール: 集約の外から内部のオブジェクトを直接変更してはいけない
  ✗ order.items[0].quantity = 5
  ✓ order.changeItemQuantity(productId, 5)
```

### ドメインイベントで「何が起きたか」を記録する

```
命令（コマンド）:   「注文を確定せよ」     → order.confirm()
事実（イベント）:   「注文が確定された」   → OrderPlaced { orderId, occurredAt }

イベントの特徴:
  • 過去形で命名する（OrderPlaced, PaymentCompleted）
  • 事実なので取り消せない
  • 他のシステムに伝播させることができる
```

### 後続の概念とのつながり

- クリーンアーキテクチャ → DDDのドメインモデルをドメイン層に置く
- マイクロサービス → 境界づけられたコンテキストを、サービス分割の指針にする
- イベント駆動 → ドメインイベントをもとに、サービス間でやり取りするイベントを作る

## 7. クリーンアーキテクチャ

### この概念が解決する問題

> 「フレームワークのバージョンアップでビジネスロジックまで書き直しになった」

クリーンアーキテクチャの目的は、**ビジネスロジックが外部の技術的詳細に依存しないようにする**ことです。クリーンアーキテクチャでは、フレームワーク、データベース、UIを「詳細」と呼び、ビジネスルールを同心円の中心に置きます。

### 同心円モデルと依存ルール

```
                ┌─────────────────────────────────────┐
                │  Frameworks & Drivers（外部層）        │
                │  Express, Prisma, 外部API              │
                │    ┌──────────────────────────────┐  │
                │    │  Interface Adapters（変換層）   │  │
                │    │  Controller, Presenter        │  │
                │    │    ┌──────────────────────┐  │  │
                │    │    │  Use Cases           │  │  │
                │    │    │（アプリケーション層）│  │  │
                │    │    │  アプリ固有のルール    │  │  │
                │    │    │    ┌──────────────┐  │  │  │
                │    │    │    │  Entities     │  │  │  │
                │    │    │    │  （ドメイン層）│  │  │  │
                │    │    │    │  ビジネスの   │  │  │  │
                │    │    │    │  核心ルール   │  │  │  │
                │    │    │    └──────────────┘  │  │  │
                │    │    └──────────────────────┘  │  │
                │    └──────────────────────────────┘  │
                └─────────────────────────────────────┘

依存ルール: 矢印は必ず内側に向かう（外 → 内）
  • 内側の層は外側の層を知らない
  • ドメイン層は Express も Prisma も知らない
  • ユースケース層は HTTP リクエストの形を知らない
```

### 各層の役割

| 層 | 責務 | 含まれるもの | 知らないこと |
|---|------|------------|------------|
| **Entities** | ビジネスルール | エンティティ、値オブジェクト、リポジトリインターフェース | HTTP, DB, フレームワーク |
| **Use Cases** | アプリのユースケース | 「注文を作成する」等の操作 | HTTPリクエストの形、DBの種類 |
| **Interface Adapters** | データ形式の変換 | Controller, Presenter, Gateway | ビジネスルールの中身（変換と受け渡しだけを行う） |
| **Frameworks & Drivers** | 技術的詳細 | Express・Prisma 本体, 環境設定 | なし |

- **Presenter**は、ユースケースの出力を、画面やAPIレスポンスの形に変換します。
- **Gateway**は、ユースケースが使うインターフェース（例: OrderRepository）を実装し、DBや外部APIとのやり取りを受け持ちます。本教材では、PrismaOrderRepositoryがGatewayです。GatewayはPrismaを呼び出しますが、Prisma本体はFrameworks & Driversに属します。

#### 同心円の層と本教材のディレクトリの対応

| 同心円の層 | 本教材のディレクトリ | 例 |
|---|---|---|
| **Entities** | domain/ | Order, Money, OrderRepository（interface） |
| **Use Cases** | application/ | PlaceOrderUseCase |
| **Interface Adapters** | presentation/controllers/・presentation/routes/（入力側）, infrastructure/persistence/（出力側＝Gateway） | OrderController, ルート定義, PrismaOrderRepository |
| **Frameworks & Drivers** | src/main.ts, infrastructure/config/, Express・Prisma 本体 | Express アプリの起動と PrismaClient の生成（src/main.ts）、infrastructure/config/ |

注: 本教材はDDDと組み合わせるため、リポジトリインターフェースをEntities（domain/）に置きます。Clean Architectureの原典では、ユースケースが使うインターフェースをUse Cases側に置く配置も示されています。

### 依存性逆転による「交換可能性」

```
テスト時:                        本番時:
  UseCase                         UseCase
    │                                │
    ▼                                ▼
  OrderRepository(interface)       OrderRepository(interface)
    │                                │
    ▼                                ▼
  InMemoryOrderRepository         PrismaOrderRepository
  （メモリ上で高速テスト）           （実際のDB操作）
```

ドメイン層（domain/）にインターフェースを置き、Gateway（infrastructure/persistence/）で実装します。こうすると、次の3つの利点があります。
- テスト時はDBなしで高速に実行
- 本番DBの変更がビジネスロジックに影響しない
- フレームワークの変更が最小限の影響で済む

### ディレクトリ構成例

```
src/
├── main.ts              # Frameworks & Drivers: Express アプリの起動、PrismaClient の生成、依存の組み立て
│
├── domain/              # Entities: ビジネスの核心
│   ├── entities/        #   Order, Product, User
│   ├── value-objects/   #   Money, Address, Email
│   └── repositories/    #   OrderRepository(interface)
│
├── application/         # Use Cases: ユースケース
│   ├── use-cases/       #   PlaceOrderUseCase, CancelOrderUseCase
│   └── dto/             #   Input/Output の型定義
│
├── infrastructure/      # 外側: 技術的詳細
│   ├── persistence/     #   Interface Adapters（出力側＝Gateway）: PrismaOrderRepository
│   ├── external/        #   外部API連携
│   └── config/          #   Frameworks & Drivers: 環境設定
│
└── presentation/        # 外側: UIとの接続
    ├── controllers/     #   Interface Adapters（入力側）: OrderController
    ├── routes/          #   Interface Adapters（入力側）: Express ルーティング
    └── middleware/       #   認証、エラーハンドリング
```

### 後続の概念とのつながり

- マイクロサービス → 各サービスの内部構造としてクリーンアーキテクチャを適用する
- イベント駆動 → ユースケース層がドメインイベントを発行し、infrastructure/の実装がブローカーへ配信する（DBへの保存と配信を確実にそろえる方法は、10章のTransactional Outboxを参照）

## 8. マイクロサービス

### この概念が解決する問題

> 「チームが10人を超えたあたりから、お互いのコード変更が衝突するようになった」

マイクロサービスは、システムを、独立してデプロイできる小さなサービスに分割するアーキテクチャスタイルです。ただし、**分割にはコストがかかります**。マイクロサービスを検討するときは、まずこのコストを理解してください。

### モノリスから段階的に分割する

```
段階1: モノリス            段階2: モジュラーモノリス    段階3: マイクロサービス
┌───────────────┐        ┌───────────────┐         ┌─────┐ ┌─────┐ ┌─────┐
│ すべてが1つの   │        │ 1つのデプロイ   │         │注文  │ │在庫  │ │決済  │
│ アプリに同居    │   →    │ だが内部は     │   →     │サービス│ │サービス│ │サービス│
│               │        │ モジュールで    │         │     │ │     │ │     │
│               │        │ 分離されている  │         │ DB  │ │ DB  │ │ DB  │
│     DB        │        │     DB        │         └─────┘ └─────┘ └─────┘
└───────────────┘        └───────────────┘

                  最初から分割しない！
                  まずモノリスで始めて、必要に応じて分割する
```

### サービス分割の判断基準

DDDの境界づけられたコンテキストが、サービスの分割単位になります。

```
分割すべきサイン:                    分割すべきでないサイン:
✓ チームが独立して開発したい          ✗ 「マイクロサービスが流行っているから」
✓ 異なるスケーリング要件がある        ✗ データを頻繁にJOINする必要がある
✓ 異なる技術スタックが最適           ✗ 分散トランザクションが必要になる
✓ 障害の影響範囲を限定したい          ✗ チームが小さい（2-3人）
```

### サービス間通信

```
同期通信                             非同期通信
┌──────┐  HTTP/gRPC  ┌──────┐      ┌──────┐  イベント  ┌───────┐  ┌──────┐
│注文   │ ──────────▶ │在庫   │      │注文   │ ────────▶│Broker │──▶│在庫   │
│サービス│ ◀────────── │サービス│      │サービス│          └───────┘  │サービス│
└──────┘   レスポンス  └──────┘      └──────┘                     └──────┘

同期: シンプル、即座に結果がわかる        非同期: 疎結合、障害に強い
     相手が落ちていると失敗する               複雑、結果整合性の考慮が必要
```

### Database per Service：各サービスが自分のDBを持つ

```
✗ 共有データベース（アンチパターン）
┌──────┐  ┌──────┐
│注文   │  │在庫   │
│サービス│  │サービス│
└──┬───┘  └──┬───┘
   │         │
   └────┬────┘
        ▼
   ┌─────────┐
   │ 共有 DB  │  ← テーブルの変更が全サービスに影響
   └─────────┘     独立デプロイが不可能になる

✓ Database per Service
┌──────┐  ┌──────┐
│注文   │  │在庫   │
│サービス│  │サービス│
└──┬───┘  └──┬───┘
   ▼         ▼
┌─────┐  ┌─────┐
│注文DB│  │在庫DB│  ← 各サービスが独自のDBを所有
└─────┘  └─────┘     他のサービスのデータはAPIを通じて取得
```

### 耐障害性パターン（Circuit Breaker）

```
         状態遷移図:

         ┌─────────────────────── 成功 ───────────────────────┐
         ▼                                                    │
    ┌─────────┐ 失敗が閾値超過  ┌──────┐ タイムアウト後 ┌───────────┐
    │ CLOSED  │ ──────────────▶ │ OPEN │ ─────────────▶ │ HALF-OPEN │
    │ (通常)  │                 │(遮断)│                │  (試行)   │
    └─────────┘                 └──────┘                └───────────┘
                                  ▲                           │
                                  │          失敗             │
                                  └───────────────────────────┘

CLOSED:  通常通りリクエストを通す
OPEN:    リクエストを即座に失敗させる（相手に負荷をかけない）
HALF-OPEN: 1つだけ試しに通して、成功すればCLOSEDに戻す
```

### 後続の概念とのつながり

- オーケストレーション → サービスのデプロイ・スケーリング・管理を自動化する
- イベント駆動 → サービス間の通信を非同期にし、結果整合性を実現する

## 9. オーケストレーション

### この概念が解決する問題

> 「サービスが10個に増えたが、デプロイに半日かかる。障害時にどのサービスが原因か分からない」

マイクロサービスの数が増えると、デプロイや障害対応を手作業で続けることが難しくなります。オーケストレーションでは、インフラの操作を自動化し、手順を標準化することで、この問題を解決します。

注: 本章のオーケストレーション（コンテナオーケストレーション）は、コンテナの配置・起動・再起動を自動で管理することを指します。10章のSagaパターンに出てくるOrchestrationは、1つのサービスが業務処理の手順を順に呼び出す方式です。この2つは別の概念です。

### コンテナ技術：アプリケーションと依存ライブラリをまとめる

```
従来の環境:                     コンテナ:
┌──────────────────┐           ┌─────────┐ ┌─────────┐ ┌─────────┐
│ サーバー          │           │ App A   │ │ App B   │ │ App C   │
│ ┌──┐ ┌──┐ ┌──┐  │           │ + 依存  │ │ + 依存  │ │ + 依存  │
│ │A │ │B │ │C │  │           └────┬────┘ └────┬────┘ └────┬────┘
│ └──┘ └──┘ └──┘  │                │          │          │
│  依存ライブラリが  │           ┌────┴──────────┴──────────┴────┐
│  衝突する可能性    │           │      コンテナランタイム         │
│                  │           │      （Docker）               │
│  OS              │           │      OS                      │
└──────────────────┘           └───────────────────────────────┘

各アプリが独立した環境を持つ → 依存の衝突がなくなる
「自分のPCでは動く」問題が解消される
```

### Kubernetes：コンテナを管理する仕組み

```
Kubernetesの主要リソース:

Pod（最小単位）
  └── Container（アプリ）
       1つ以上のコンテナをまとめた単位

Deployment（レプリカ管理）
  └── Pod × N個（レプリカ数を宣言的に管理）
       「常に3つのPodを維持せよ」→ 1つ落ちたら自動で再作成

Service（ネットワーク）
  └── 複数のPodへのトラフィック分散
       「order-service」という名前でアクセスすると
       背後の3つのPodに負荷分散

Ingress（外部公開）
  └── 外部からのHTTPトラフィックをServiceに振り分け
       api.example.com/orders → order-service
       api.example.com/users  → user-service
       ※ Ingress の代表的な実装である ingress-nginx は、2026年3月に保守を終了した。
         外部公開の方法は Ingress だけではない。後継として Gateway API
         （Gateway, HTTPRoute などのリソース）がある
```

### サービスメッシュ：サービス間通信をアプリの外で制御する

サービスが増えると、通信に関わる処理を、すべてのサービスのコードに書く必要が出てきます。たとえば、リトライ、タイムアウト、mTLS（サービス間の相互認証つき暗号化）、通信のトレースです。サービスメッシュは、これらの処理を各サービスの外側にあるプロキシで行います。そのため、アプリのコードを変えずに通信を制御できます。代表例はIstioとLinkerdです。従来は、Podごとにプロキシ（サイドカー）を置く方式でした。Istioは、ノード単位でプロキシを置くambient modeも提供しています（2024年にGA）。サービス数が少ないうちは、導入による効果よりも運用の手間の方が大きくなります。

### デプロイ戦略

```
ローリングアップデート:
  v1 v1 v1 → v2 v1 v1 → v2 v2 v1 → v2 v2 v2
  段階的に新バージョンに置き換え。ダウンタイムなし。

ブルーグリーン:
  [Blue: v1] ← トラフィック
  [Green: v2] ← 待機
  切り替え時にトラフィックをGreenに向ける。即座にロールバック可能。

カナリアリリース:
  v1 ← 90%のトラフィック
  v2 ← 10%のトラフィック
  問題がなければ徐々にv2の割合を増やす。リスクを最小化。
```

### CI/CD：ビルド・テスト・デプロイの手順を自動化する

```
コード変更
    │
    ▼
┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
│  Build  │──▶│  Test  │──▶│  Push  │──▶│ Deploy │
│  構築   │   │ テスト  │   │ イメージ│   │ 配備   │
│        │   │        │   │ 登録   │   │        │
└────────┘   └────────┘   └────────┘   └────────┘
  CI（継続的インテグレーション）    CD（継続的デリバリー）
                                    本番への配備まで自動にしたものを
                                    継続的デプロイメントと呼ぶ

  自動化により:
  • 人的ミスが減る
  • デプロイ頻度が上がる
  • 問題の早期発見ができる
```

## 10. イベント駆動アーキテクチャ

### この概念が解決する問題

> 「注文サービスが在庫サービスを呼び、在庫が決済を呼び...。1つのサービスが落ちると連鎖的に全体が止まる」

イベント駆動は、サービス間を疎結合にし、サービス同士を非同期で連携させるアーキテクチャスタイルです。

### コマンドとイベントの違い

```
コマンド（命令）:                   イベント（事実）:
「注文を確定せよ」                  「注文が確定された」
 → 特定の相手に送る                 → 不特定多数に通知
 → 失敗する可能性がある              → すでに起きた事実
 → 命令形で命名                     → 過去形で命名
   PlaceOrder                        OrderPlaced
   ProcessPayment                    PaymentCompleted
   ShipOrder                         OrderShipped
```

### メッセージブローカー

```
キュー型（RabbitMQ, SQS）:          ストリーム型（Kafka）:
1つのメッセージ → 1つのコンシューマ    1つのイベント → 複数のコンシューマ

Producer → [Queue] → Consumer       Producer → [Topic] → Consumer A
                                                      → Consumer B
                                                      → Consumer C

処理したら消える                      永続的に保存、再読み込み可能
タスク分散向き                        イベント伝播向き
```

### CQRS：読み書きの責務を分離する

CQRSには、分離の度合いによって段階があります。第9回では、次の3つのレベルに分けて扱います。

| レベル | 分離するもの | 内容 |
|---|---|---|
| レベル1 | コードパス | 同じDB・同じモデルで、書き込みと読み取りのコードパスを分ける |
| レベル2 | モデル | 同じDBで、読み取り専用のモデル（例: 一覧表示用のクエリ型）を別に持つ |
| レベル3 | データストア | 読み取り専用のDBを分け、イベントで同期する（下の図） |

```
従来:                              CQRS（レベル3）:
 ┌─────────────┐                    ┌──────────┐    ┌──────────┐
 │  同じモデルで │                    │ Write    │    │ Read     │
 │  読み書き    │                    │ Model    │    │ Model    │
 │             │                    │          │    │          │
 │  Order      │                    │ Order    │    │ OrderView│
 │  (正規化)   │                    │ (正規化) │    │ (非正規化)│
 └──────┬──────┘                    └────┬─────┘    └────┬─────┘
        │                               │  イベント     │
     ┌──┴──┐                          ┌──┴──┐       ┌──┴──┐
     │ DB  │                          │Write│       │Read │
     └─────┘                          │ DB  │       │ DB  │
                                      └─────┘       └─────┘

なぜ分離するか:
  例: 注文一覧画面のために注文・顧客・商品を毎回 JOIN すると遅い。
      しかし書き込み側のモデルを画面に合わせて崩すと、バリデーションのルールが崩れる。
  • 読み取りは高速な非正規化データが最適
  • 書き込みは整合性重視の正規化データが最適
  • 読み書きの負荷が大きく異なる場合に有効
```

注意: 多くのアプリはレベル1で足ります。レベル3は、結果整合性を受け入れられる場合だけ選びます。

### 結果整合性：「いつか整合する」という考え方

```
強い整合性（従来のDB）:              結果整合性（分散システム）:
  書き込み → 即座に全員が最新を見る     書き込み → しばらくは古いデータが見える
  シンプルだが、分散環境では困難           → 数秒〜数分で全体が整合する

例: SNSの「いいね」数
  ユーザーAが「いいね」 → ユーザーBが見る: まだ反映されていない
                       → 数秒後: 反映される
  → これで十分なケースは多い
```

### Sagaパターン：分散トランザクションの代替

```
従来のトランザクション:                Sagaパターン:
  BEGIN                               各サービスがローカルトランザクションを実行
    注文確定                            失敗時は補償トランザクションで、
    在庫減少                            成功済みのステップを打ち消す処理を行う
    決済処理
  COMMIT or ROLLBACK

  ← サービスごとに DB が分かれると、1つのトランザクションでは囲めない。
    2PC（2相コミット）で囲む方法もあるが、どれか1つのサービスが止まると
    全体が待たされるため、マイクロサービスでは避けることが多い

Choreography（振り付け）:
  注文確定 ──▶ OrderPlaced ──▶ 在庫引当 ──▶ StockReserved ──▶ 決済処理 ──▶ PaymentCompleted
                                                                          ├─▶ 注文サービス: 注文の決済完了を記録する
                                                                          └─▶ 通知サービス: 確認メールを送る

  失敗時（補償トランザクション）:
    在庫引当の失敗 ──▶ StockReservationFailed ──▶ 注文サービス: 注文取消
    決済処理の失敗 ──▶ PaymentFailed ──┬─▶ 在庫サービス: 引当解除
                                       └─▶ 注文サービス: 注文取消

Orchestration（指揮）:
  ┌────────────────────┐
  │ Saga Orchestrator   │
  │  1. 注文確定 → 成功 │
  │  2. 在庫引当 → 成功 │
  │  3. 決済処理 → 失敗 │
  │  → 2を補償（引当解除）│
  │  → 1を補償（注文取消）│
  └────────────────────┘
```

注: SagaのOrchestrationは、1つのサービス（Orchestrator）が業務処理の手順を順に呼び出す方式です。9章のコンテナオーケストレーション（コンテナの配置・起動・再起動を自動で管理すること）とは別の概念です。

### Transactional OutboxでDBへの保存とイベント送信をそろえる

「DBに保存」と「ブローカーに送信」は別の書き込みです。保存の直後にプロセスが落ちると、イベントは送られません。実務では、注文と同じトランザクションでoutboxテーブルにイベントを書き、別のプロセスがそれを読んでブローカーへ送ります。この方法を「Transactional Outboxパターン」と呼びます。

### 冪等性：同じ操作を何度実行しても結果が同じ

```
ネットワーク障害で同じメッセージが2回届く可能性がある:

✗ 非冪等: processPayment(orderId, 1000円)
  → 2回実行すると2000円引かれる！

✓ 冪等: processPayment(eventId: "evt-123", orderId, 1000円)
  → eventIdで処理済みかチェック
  → 2回目は「すでに処理済み」としてスキップ
```

注意: 「確認してから処理」を別々に行うと、同時に届いた2通がどちらも確認を通過します。また、処理した後、記録する前にプロセスが落ちると、もう一度処理されます。防ぐ方法は次の2つです。

1. 処理済みテーブルのeventIdに一意制約を付け、本処理と同じトランザクションでINSERTする。
2. 決済APIなどに冪等キー（例: orderId）を渡し、相手側で、同じキーのリクエストを2回処理しないようにしてもらう。

## 11. 概念のスケール感

すべての概念をスケール（扱う範囲の大きさ）で整理すると、次の図になります。各概念がコード・アプリ・システムのどのレベルを扱うかを、この図で比べられます。

```
                        コード      アプリ      システム
                        レベル      レベル      レベル
                        ─────      ─────      ──────
SOLID原則               ████
カプセル化              ████
ポリモーフィズム          ████

正規化                  ████
ACID / トランザクション   ████
インデックス             ████

データモデリング          ████ ██████

デザインパターン          ████ ██████

DDD（戦術的設計）         ████ ██████
DDD（戦略的設計）              ██████ ██████

クリーンアーキテクチャ          ██████

マイクロサービス                ██████ ██████
オーケストレーション                   ██████
イベント駆動                          ██████

共通する原則:
  ┌──────────────────────────────────────────────┐
  │  • 関心の分離（責務を明確に分ける）              │
  │  • 疎結合（変更の影響を局所化する）              │
  │  • 抽象化（詳細を隠し、本質を明示する）          │
  │  • トレードオフ（銀の弾丸はない）               │
  └──────────────────────────────────────────────┘
```

### 概念間の「同じ原則の異なるスケール」

多くの概念は、同じ原則を、異なるスケールに当てはめたものです。

| 原則 | コードレベル | アプリレベル | システムレベル |
|------|------------|------------|--------------|
| 責務の分離 | 単一責任の原則 | レイヤー分離 | サービス分割 |
| 依存の制御 | 依存性逆転の原則 | ポート＆アダプター | API Gateway |
| 変更の局所化 | カプセル化 | 境界づけられたコンテキスト | Database per Service |
| 通知と連携 | Observerパターン | ドメインイベント | イベント駆動アーキテクチャ |
| データアクセスの抽象化 | Repositoryパターン | データアクセスの実装を外側の層（Gateway）に分離 | API Composition |

### 最も大切なこと

> **「正解は1つではない。トレードオフを理解し、根拠を持って判断できること」**

アーキテクチャに唯一の正解はありません。設計する人に求められるのは、次の4つです。

1. 選択肢を知っていること：比較できる設計案を多く挙げられる
2. トレードオフを説明できること：「Xを得る代わりにYを犠牲にする」
3. 文脈に応じて判断できること：チーム規模、要件、制約を考慮する
4. 判断の根拠を言語化できること：チームに共有し、議論できる

本ワークショップは、この4つを合わせた **「設計判断力」** を身につけるためのプログラムです。
