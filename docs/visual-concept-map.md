## 2. Observerパターンの進化 — コードからシステムへ

同じ「通知」の概念が、スケールによってどう形を変えるかを示します。

```
スケール: コードレベル
────────────────────
  class EventEmitter {
    emit('OrderPlaced', event)
  }
  → 同一プロセス内で通知
  → 第4回 デザインパターン（Observer）


スケール: アプリケーションレベル
────────────────────
  class DomainEventPublisher {
    publish(new OrderPlaced(...))
  }
  → ドメインイベントとして意味を持つ
  → 第5回 DDD（ドメインイベント）
  → 第6回 クリーンアーキテクチャ（ユースケースから発行）


スケール: システムレベル
────────────────────
  Kafka/RabbitMQ
  ┌──────┐  OrderPlaced  ┌────────┐
  │Order │ ─────────────▶│Broker  │──▶ InventoryService
  │Svc   │               │        │──▶ PaymentService
  └──────┘               │        │──▶ NotificationService
                         └────────┘
  → サービス間の非同期通信
  → 第9回 イベント駆動アーキテクチャ
```

※ この図は、Observer の「1つの出来事を複数の受け手に届ける」形を示すための簡略図です。第9回の Saga は順番に進む形です。在庫サービスが OrderPlaced を受けて StockReserved を出し、決済サービスは StockReserved を、通知サービスは PaymentCompleted を受けてから動きます（4章の図を参照）。

                                       注文サービス: 注文の決済完了を記録する
                                       通知サービス: 確認メールを送る
```

図の右側に書いた「〜層」は、クリーンアーキテクチャの同心円の層の名前です。ディレクトリとの対応は、1章の下の表を参照してください。

> **注意:** 「4. 保存」（DBに保存）と「5. イベント発行」（ブローカーに送信）は、別々の書き込みです。保存の直後にプロセスが異常終了すると、イベントは送られません。実務では、注文と同じトランザクションで outbox テーブルにイベントを書き、別のプロセスがそれを読んでブローカーへ送る「Transactional Outbox パターン」を使います。

**Saga の補償（失敗したステップの前までの結果を打ち消す処理）**

| 失敗したステップ | 発行するイベント | 補償を実行するサービスと内容 |
|---|---|---|
| 在庫引当 | StockReservationFailed | 注文サービスが注文をキャンセル済みにする（※） |
| 決済 | PaymentFailed | 在庫サービスが、引当した分を解除する（引当解除）。注文サービスが注文をキャンセル済みにする |

※ この図は、第9回 README のコレオグラフィの図と同じ直列の形です。在庫サービスが在庫引当を終えてから StockReserved を発行し、決済サービスはそのイベントを受けてから決済します。そのため、在庫引当が失敗した時点では、決済はまだ行われていません。在庫も引き当てられていません。補償は注文の取消だけです。

## 5. 「なぜ」の連鎖 — 概念が必要になる理由のつながり

```
「コードの変更が予期せぬ場所に波及する」
    │
    ▼ だから
「責務を分離し、依存を制御する」 → SOLID原則、カプセル化
    │
    ▼ すると
「繰り返し現れる設計問題に名前がつく」 → デザインパターン
    │
    ▼ さらに
「ビジネスの言葉でコードを書きたい」 → DDD
    │
    ▼ でも
「ビジネスロジックがDB/HTTP/FWに依存している」
    │
    ▼ だから
「レイヤーで依存方向を制御する」 → クリーンアーキテクチャ
    │
    ▼ やがて
「チームが大きくなり、1つのアプリでは開発が衝突する」
    │
    ▼ だから
「サービスを分割して独立にデプロイする」 → マイクロサービス
    │
    ▼ すると
「サービスが増えて手作業の運用が追いつかない」
    │
    ▼ だから
「インフラを自動化し標準化する」 → オーケストレーション
    │
    ▼ 同時に
「同期通信だとサービスが連鎖的に落ちる」
    │
    ▼ だから
「イベントで疎結合に連携する」 → イベント駆動
    │
    ▼ ただし
「結果整合性、冪等性、補償処理の複雑さが増す」
    │
    ▼ だから
「トレードオフを理解し、文脈に応じて判断する」 → 設計判断力
```

## 7. よくある設計判断とその根拠

ワークショップで学ぶ概念を使って、実際の判断がどう行われるかの例です。

```
判断1: 「モノリスのままか、マイクロサービスに分割するか？」
──────────────────────────────────────────────────────

  判断に必要な知識:
  ├── DDD: 境界づけられたコンテキストの識別（第5回）
  ├── マイクロサービス: 分割のメリット・コスト（第7回）
  └── イベント駆動: 分割後の通信方式（第9回）

  判断基準:
  ├── チーム規模が10人以下 → モジュラーモノリスで十分
  ├── スケーリング要件がサービスごとに異なる → 分割を検討
  └── データの結合が強い → 分割すべきではない


判断2: 「同期通信か、非同期通信か？」
──────────────────────────────────────────────────────

  判断に必要な知識:
  ├── マイクロサービス: 通信パターン（第7回）
  ├── イベント駆動: 結果整合性のトレードオフ（第9回）
  └── RDB: ACID vs 結果整合性（第2回、第9回）

  判断基準:
  ├── 即座にレスポンスが必要 → 同期（REST/gRPC）
  ├── 処理の失敗を呼び出し側に伝える必要 → 同期
  ├── 処理に時間がかかる → 非同期（キュー）
  └── 複数のサービスに通知したい → 非同期（イベント）


判断3: 「CQRSを導入するか？」
──────────────────────────────────────────────────────

  判断に必要な知識:
  ├── RDB: 正規化と非正規化のトレードオフ（第2回）
  └── イベント駆動: CQRS の3レベル（第9回）

  判断基準:
  ├── 読み書きの負荷が大きく異なる → 導入を検討
