# 改善提案まとめ

> 本ドキュメントは、アーキテクチャ登竜門の今後の進め方について、改善点・参加者がつまずきやすいポイント・追加トピックの提案をまとめたものです。

---

## 1. 参加者がつまずきやすいポイントと対策

### 1-1. フェーズの切り替わりで難易度が上がる

3フェーズ構成のうち、特に次の切り替わりで、参加者は難しさを感じやすい。

| 遷移 | 難しさの原因 | 対策案 |
|------|-------------|--------|
| 第3回（データモデリング）→ 第4回（デザインパターン） | データ中心の思考からオブジェクト設計への切り替え | フェーズ2冒頭に「なぜ設計パターンが必要になるのか」をデータモデリングの課題から導入 |
| 第4回（デザインパターン）→ 第5回（DDD） | 技術パターンから戦略的設計への抽象度上昇 | DDDの前に「前提知識チェックリスト」を事前配布。オブジェクト指向・データモデリングの知識がDDDでどう使われるかを明示 |
| 第6回（クリーンアーキテクチャ）→ 第7回（マイクロサービス） | 単一アプリ内の設計から分散システムへの移行 | 「モノリスの限界」を具体的に体験するシナリオを用意し、なぜサービス分割が必要になるかを動機づける |

具体的なアクションは次の2つ。
- 各フェーズの最初の回（第4回・第7回）で、前のフェーズとのつながりを示す。時間配分は変えず、事前読み物に「前のフェーズとのつながり」を1ページ追加するか、講義の最初のセクション（第4回「デザインパターンとは（10分）」、第7回「モノリスからマイクロサービスへ（15分）」）の中で扱う。既存の[回をまたぐ「つなぎ台本」](session-bridge-scripts.md)も使える
- 「前のフェーズで学んだXが、このフェーズではYとして使われる」を明示するスライドを用意

### 1-2. 抽象概念と実務の距離感

DDDの「ユビキタス言語」や「境界づけられたコンテキスト」、クリーンアーキテクチャの「依存性逆転」など、概念としては理解できても「明日の仕事でどう使うか」がイメージしにくい。

対策案は次のとおり。
- 各回の講義時間は変えずに、「実務適用シナリオ」を事前読み物または課題として提供する（例: `practical-scenarios.md`）
  - 「あなたのチームのコードベースにこの概念を適用するとしたら？」を、課題の中で考えてもらう
  - Before/After形式で、実際にありがちなコードのリファクタリング例を提示
- `workshops/XX-*/practical-scenarios.md` として、実務寄りのケーススタディを別ファイルで提供

### 1-3. コード例が「見るだけ」になっている

現状のTypeScriptコード例はMarkdown内の提示のみで、参加者が手を動かす機会が少ない。

対策として、次の環境を用意する。
- `exercises/` ディレクトリを新設し、各回のコード例を実行可能なTypeScriptプロジェクトとして提供
- `package.json` + `tsconfig.json` を整備し、次のコマンドで演習を実行できるようにする

```bash
npm install
npm run exercise:01  # 第1回の演習を実行
npm run exercise:02  # 第2回の演習を実行
```

- 各演習にテストを付けて、参加者が自分の理解を検証できるようにする
- 例: 「このクラスをSOLID原則に沿ってリファクタリングせよ。テストが全て通ればOK」

### 1-4. 課題の模範解答がない

`schedule.md` で各回の課題出題は言及されているが、模範解答や解説が存在しない。参加者が自学自習する際の指針がない。

対策案は次のとおり。
- 各ワークショップに `homework-solutions.md` を追加
- 講師が課題のフィードバックを行った後に参加者に共有する想定
- 「正解は1つではない」ことを示すため、複数のアプローチとそのトレードオフを提示

## 2. カリキュラム構造の改善

### 2-1. 中間振り返りの構造化

`schedule.md` にWeek5の中間振り返り（任意）とあるが、内容が未定義。

**提案: `workshops/mid-review/` を新設**

内容は次のとおり。
- フェーズ1の理解度セルフチェック（10問程度）
- フェーズ1の概念がフェーズ2でどう使われるかのプレビュー
- 参加者同士のペアレビュー（課題の振り返り）
- ここまでの疑問点の共有と解消

### 2-2. 学習成果の可視化

参加者の成長を測る仕組みが少ない（KPTは最終回のみ）。

**提案: 設計力セルフアセスメント**

- 第0回の前に、各テーマの自信度を1〜5で評価する（事前）
- 第10回の前に、同じアセスメントを再び記入する（事後）
- 事前・事後の差分を可視化し、成長を実感できるようにする
- `docs/assessment-template.md` としてテンプレートを提供（後述）

### 2-3. 一貫したサンプルプロジェクトの導入

各回の講義のコード例は、主にECサイトの注文ドメインを使っている。ただし題材として明文化されておらず、第1回のBankAccount・Animalや第3回のコード課題（タスク管理ツール）のように別の題材も混ざっている。

**提案: 注文ドメインを全回の通しの題材として明文化する**

| 回 | 適用する学び |
|----|------------|
| 第1回 | Orderクラスの設計（カプセル化、SOLID） |
| 第2回 | orders・order_itemsテーブルの正規化とインデックス |
| 第3回 | 注文ドメインの概念/論理/物理モデル（コード課題の題材をそろえるか検討） |
| 第4回 | Strategy（価格計算）、Observer（注文状態の通知）、Repository |
| 第5回 | 注文の集約とOrderPlacedイベント |
| 第6回 | 注文確定ユースケースのレイヤー分離 |
| 第7回 | 注文サービス・在庫サービス・決済サービスの分割検討 |
| 第8回 | 注文サービスのコンテナ化とCI/CD（講師のデモ） |
| 第9回 | OrderPlaced → StockReserved → PaymentCompletedのSaga（コレオグラフィ） |

題材を明文化すると、参加者は各回のコード例を同じ注文ドメインの続きとして読める。前の回で作ったOrderクラスやテーブルが、次の回でどう変わるかを確認しやすくなる。

## 3. プラスアルファ：開発手法・追加トピック

### 3-1. テスト戦略（強く推奨）

**なぜ必要か**：クリーンアーキテクチャの利点のひとつは、テストを書きやすくなること（テスタビリティ）である。第6回には各レイヤーのテスト戦略の表があるが、テストダブルの使い分けやTDDのサイクルは扱っていない。

カバーすべき内容は次のとおり。
- テストピラミッド（単体テスト / 統合テスト / E2Eテスト）
- 依存性注入とモックの関係（なぜレイヤー分離がテストを容易にするか）
- テストダブルの使い分け（Mock / Stub / Spy / Fake）
- TDDの基本サイクル（Red → Green → Refactor）

追加方法の選択肢は次の2つ。
1. 第6回の講義時間は変えずに、テストダブルとTDDを扱う補足資料（`docs/testing-strategy.md`）を作り、第6回の事前読み物または課題で使う
2. 独立した回として追加（全12回に拡張）

### 3-2. アジャイル開発手法とアーキテクチャの関係（推奨）

**なぜ必要か**：参加者が「最初から完璧なアーキテクチャを設計しなければならない」と誤解するおそれがある。アーキテクチャは、要件の変化に合わせて段階的に変えていく。そのため、アジャイル開発と組み合わせた進め方を知っておく必要がある。

カバーすべき内容は次のとおり。
- Evolutionary Architecture（進化的アーキテクチャ）：アーキテクチャを変更し続ける前提で設計する
- YAGNI原則：必要になるまで作らない
- ADR（Architecture Decision Records）：設計判断の記録
- 技術的負債の管理：意図的な負債と無意識の負債
- フィーチャーフラグ、ストラングラーパターン：段階的な移行手法

追加方法の選択肢は次の3つ。
1. オリエンテーション（第0回）の「学習の進め方（15分）」の中で一言触れる（時間配分は変えない）
2. 最終回（第10回）の「振り返りと次のステップ（25分）」の中で、既存の段階的導入の説明に含める（時間配分は変えない）
3. `docs/development-methodology-guide.md` として補足資料化（後述で作成）

### 3-3. 可観測性（Observability）（推奨）

**なぜ必要か**：分散システム（フェーズ3）では、システムの内部状態を外部から把握できることが運用の前提。設計段階から可観測性を意識する必要がある。

カバーすべき内容は次のとおり。
- 可観測性のための3種類のデータ（ログ、メトリクス、分散トレーシング）
- OpenTelemetryの概要
- SLI / SLO / エラーバジェットの考え方
- 構造化ログとコリレーションID

**追加方法**：第7回で扱っている可観測性のための3種類のデータを前提に、SLI/SLO/エラーバジェットと構造化ログ・コリレーションIDを扱う補足資料（`docs/observability-basics.md`）を作る。第7回・第8回の講義時間は変えない。

### 3-4. セキュリティ設計の基礎（検討）

**なぜ必要か**：第10回で「扱わなかったテーマ」として言及されているが、認証・認可はほぼすべてのシステムで必須。

カバーすべき内容は次のとおり。
- 認証（Authentication）vs 認可（Authorization）
- OAuth 2.0 / OpenID Connect の概要
- OWASP Top 10の概要
- セキュリティを意識したアーキテクチャ（ゼロトラスト、最小権限の原則）

**追加方法**：`docs/security-basics.md` として補足資料にする

### 3-5. API設計（検討）

**なぜ必要か**：第7回（マイクロサービス）でAPI通信に触れるが、API自体の設計原則（命名規則、バージョニング、エラーハンドリング）を体系的に学ぶ機会がない。

カバーすべき内容は次のとおり。
- REST API設計の原則（リソース指向、ステータスコード、HATEOAS）
- GraphQL：いつ・なぜ選ぶか
- gRPC：マイクロサービス間通信での利点
- APIバージョニング戦略
- OpenAPI（Swagger）によるAPI定義

**追加方法**：第7回（マイクロサービス）の補足資料として追加

## 4. 優先度マトリクス

### すぐ取り組むべき（効果: 高 / 工数: 中）
1. **注文ドメインを通しの題材として明文化する**：各回のコード例が同じ題材の続きであることを参加者に示す
2. **実行可能な演習環境の整備**：参加者がコード例を読むだけでなく、自分で実行して確かめられるようにする
3. **課題の模範解答**：参加者が自学自習で答えを確かめられるようにする

### 次のイテレーションで（効果: 中〜高 / 工数: 中）
4. **テスト戦略の補足資料**：テストダブルとTDDを補い、クリーンアーキテクチャでテストを書きやすくなることを確認できるようにする
5. **実務適用シナリオ**：各回の概念を自分の業務にどう適用するかを、参加者が考えられるようにする
6. **中間振り返り**：途中で参加をやめる人を減らし、理解度を確認する
7. **アジャイル開発手法との関連**：「完璧な設計を最初から」という誤解を防ぐ

### 余裕ができたら（効果: 中 / 工数: 低〜中）
8. 可観測性の補足資料
9. セキュリティ基礎資料
10. API設計ガイド
11. 学習成果アセスメントテンプレート
